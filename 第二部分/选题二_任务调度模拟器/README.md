# 任务调度模拟器

《数据结构实践》选题二：用队列、优先队列和线性表实现一个单处理器任务调度模拟器，把 FCFS、非抢占式优先级调度、时间片轮转三种策略跑出来，用甘特图展示执行过程，并对比它们的等待时间、周转时间与响应时间。

## 环境要求

只需要 **Python 3.10 或更高版本**（开发环境为 Python 3.14）。图形界面使用 Python 标准库自带的 Tkinter，**不需要安装任何第三方包**。

```bash
py -c "import tkinter; print('Tkinter', tkinter.TkVersion)"
```

能打印出版本号就可以直接运行。

## 运行

```bash
py run.py
```

## 界面操作

| 操作 | 效果 |
|---|---|
| 工具栏"算法" | 在 FCFS / 优先级调度 / 时间片轮转之间切换（切换后自动重置到 t=0） |
| 工具栏"时间片 q" | 设置 RR 的时间片，只在选中时间片轮转时可用 |
| 工具栏"速度" | 演示速度（只影响观感，**不影响任何调度结果**） |
| **开始 / 继续** | 按当前速度连续推进模拟 |
| **暂停** | 停在当前时刻 |
| **单步** | **推进一个模拟时间单位**（任务书对单步的定义） |
| **重置** | 回到 t=0，任务状态全部复原 |
| ＋ 添加任务 / 修改 / 删除 | 编辑任务数据，**只在模拟开始前或重置后才可用** |
| 导入数据… | 从 CSV / JSON 文件载入任务 |
| 另存任务… | 把当前任务表存成 CSV（在界面上改完任务后可以留存） |
| 导出结果… | 把每个任务的开始 / 完成时刻与三项统计指标写成 CSV |
| 对比三种算法 | 同一组任务在三种算法（RR 还会试多个时间片）下各跑一遍，列成对比表 |

任务列表里，正在运行的任务高亮为绿色、就绪任务为蓝色、已完成的变暗；甘特图最上面一行是"处理器"视角的完整时间线（虚线槽表示处理器空闲），下面每个任务一行，被切成几段就说明被抢占了几次。

## 三种算法

| 算法 | 就绪队列结构 | 选谁运行 | 时间/空间复杂度 |
|---|---|---|---|
| **FCFS** | FIFO 队列（`deque`） | 队首，且一旦开始不被打断 | O(B) / O(n) |
| **优先级调度** | 二叉堆（`heapq`） | 优先级最高者（数值最小），非抢占 | O(B log n) / O(n) |
| **时间片轮转** | FIFO 队列（`deque`） | 队首，用完一个时间片未完成则回队尾 | O(B) / O(n) |

其中 n 是任务数，**B = ΣBᵢ 是所有任务运行时长之和**。三种算法都不能笼统写成 O(n)——真正决定耗时的是"所有任务加起来要跑多久"。

三个算法的区别只有"从就绪集合里挑谁"这一步，其余（时间怎么走、任务何时到达、何时算完成）完全共用同一套引擎。

## 数据集

启动时自动扫描 `data/` 目录下的 `.csv` 与 `.json`：

| 文件 | 特点 | 用来观察 |
|---|---|---|
| `sample` | 任务书给的示例数据（4 个任务，总时长 11） | 手工核对的基准，FCFS 预期结果 6.50 / 3.75 / 3.75 |
| `simultaneous` | 四个任务全部在 t=0 到达 | 同时到达时 FCFS 与优先级调度结果完全相同 |
| `mixed` | 1 个长任务 + 5 个短任务 | 长任务对其他任务等待时间的影响，RR 的优势最明显 |
| `batch` | 三批任务，中间隔了较长时间 | 处理器空闲区间的记录 |
| `priority_mix` | 优先级跨度 1~9 | 低优先级任务被长期压后 |

## 数据文件格式

**CSV**（推荐）：

```csv
task_id,name,arrival_time,burst_time,priority
T1,任务A,0,5,2
```

**JSON**：

```json
{"name": "示例数据",
 "tasks": [{"task_id": "T1", "name": "任务A",
            "arrival_time": 0, "burst_time": 5, "priority": 2}]}
```

字段约束：`task_id` 唯一非空、`name` 非空、`arrival_time` 非负整数、`burst_time` **正整数**（不能为 0）、`priority` 非负整数且**数值越小优先级越高**。任何一条不满足都会在载入阶段被拒绝并指出具体是哪个任务、哪个字段。

## 测试

```bash
py tests/test_scheduler.py     # 正确性测试
py tests/test_cross_check.py   # 交叉验证（另一份独立实现逐格比对）
py tests/test_ui.py            # 界面交互测试
py tools/benchmark.py          # 对比实验（报告第四章的数据来源）
```

`test_scheduler.py` 包含 17 组、三万余个断言，覆盖：

- **任务书给出的预期结果** —— 示例数据的 FCFS 结果逐格硬编码成断言；
- **手工推演核对** —— 优先级调度与 RR 的结果也与手算表逐项比对；
- **RR 的边界规则** —— "恰好在时间片结束时到达的任务先入队、未完成的当前任务后回队尾"，用一个最小例子把两种写法的差别逼出来；
- **五条不变量** —— 用 60 轮随机数据（3 种算法 × 3 个时间片）验证：甘特图连续无缝、每个任务的累计执行时长等于它的运行时长、任务不会在到达前运行、统计公式自洽、非抢占算法下任务不被切分；
- **可复现性** —— 同样输入连跑十次结果完全相同；跑过别的算法后再跑一次，结果不受影响；
- **输入校验** —— 重复编号、负数时间、零时长、非整数、字段缺失、空列表等。

`test_cross_check.py` 另外做一层更强的验证：把同一套调度规则**用完全不同的代码路径再实现一遍**（就绪集合用普通 list、优先级靠线性扫描、到达处理靠每格全表扫描），然后用 80 组随机数据逐格比对两张甘特图。两条路只有"规则"是共用的，任何一处编码疏漏都会让某一组对不上。

## 文件结构

```
run.py                      程序入口
src/
  models.py                 任务模型、执行记录、统计指标
  scheduler.py              三种调度算法
  engine.py                 逐时间单位的模拟引擎
  loader.py                 数据读写与校验
  ui/
    app.py                  主窗口与演示调度
    gantt.py                甘特图画布
    task_table.py           任务列表控件
    report_panel.py         状态与结果面板
    theme.py                配色与字体
data/                       五份测试数据
tests/test_scheduler.py     正确性测试
tools/benchmark.py          对比实验
docs/
  实验报告.md
  screenshots/              界面截图
```

分层严格：`scheduler.py` 只回答"下一个运行谁"，`engine.py` 只管时间怎么走，`ui/` 只负责把状态画出来。界面代码里没有任何调度判断，引擎代码里也没有任何绘图逻辑。

## 已知限制

- 按任务书要求**不计上下文切换开销**（但换人次数会被统计出来，见报告 4.4 节）；
- 单处理器，不支持多核并行；
- 任务不阻塞，不模拟 I/O 等待；
- 优先级静态不变，低优先级任务可能长期得不到处理器。

报告 5.4 节列出了改进方向（SJF/SRTF、优先级老化、切换开销建模、随机任务生成等）。
