# 城市交通路径导航系统

《数据结构实践》选题一：把城市轨道交通网络抽象成图 `G = (V, E)`，用三种搜索算法分别回答"怎么走最快"和"怎么走换乘最少"，并把搜索过程可视化。

## 环境要求

只需要 **Python 3.8 或更高版本**（开发环境为 Python 3.14）。图形界面使用 Python 标准库自带的 Tkinter，**不需要安装任何第三方包**。

验证环境是否就绪：

```bash
py -c "import tkinter; print('Tkinter', tkinter.TkVersion)"
```

如果这条命令能打印出版本号，就可以直接运行。若提示找不到 `tkinter`，说明安装 Python 时没有勾选 tcl/tk 组件，重新运行官方安装包并勾选即可。

## 运行

```bash
py run.py
```

| 滚轮 | 以鼠标位置为中心缩放 |
| 按住左键拖动 | 平移视图 |
| 双击画布 | 回到全览 |
| 工具栏"开始搜索" | 播放搜索动画 |
| 工具栏"暂停" / "继续" | 暂停或继续动画 |
| 工具栏"重置" | 清除搜索结果，保留起终点 |
| 工具栏"对比三种算法" | 一次性跑完三种算法并列出对比表 |
| 工具栏"＋ 添加线路" | 在弹出的对话框里连接两个已有站点，新建一条线路 |
| 工具栏"速度"滑块 | 调整动画播放速度（只影响观感，不影响结果） |

### 动态增删

网络可以在运行时修改：

- **删除站点**：右键站点 → "删除站点"。经过该站的线路会在这一处**断开**，断点前后的两站不会自动相连（列车不可能跳过一座车站）；原线路若被切成多段，每段长度不少于 2 的会各自保留为一条新线路。
- **添加线路**：点工具栏的"＋ 添加线路"，选择两个已有站点即可新建一条直连线路。

修改之后，起点/终点下拉框、画布和统计面板都会立即刷新。所有编辑都作用在内存中的 `Graph` 对象上，不会写回磁盘文件。

搜索过程中，**蓝色**表示位于前沿（已进入堆或队列但尚未确定）的站点，**橙色**表示已被算法确定（settle）的站点。搜索结束后，结果路径以加粗高亮显示，右侧面板给出统计数字和换乘指引。

## 三个算法

| 算法 | 优化目标 | 核心数据结构 | 适用场景 |
|---|---|---|---|
| **Dijkstra** | 总里程最短 | 二叉堆 `heapq` | 只关心"最快"或"最短" |
| **A\*** | 总里程最短 | 二叉堆 + 启发函数 `h(n)` = 到终点的欧几里得直线距离 | 同 Dijkstra，但搜索范围小得多 |
| **最少换乘 BFS** | **换乘次数最少** | 二叉堆（状态为「站点 × 线路」） | 对换乘敏感、愿意多坐几站 |

前两者的目标是同一个，只是搜索策略不同；第三个的目标与前两者不同，因此**在某些起终点上会给出不同的路径**。

**推荐演示案例**（两个指标给出不同答案，正是本项目要说明的问题）：

| 数据集 | 起终点 | Dijkstra / A\* | 最少换乘 BFS |
|---|---|---|---|
| `demo` | 东湖 → 西山 | 14.300 km，换乘 2 次 | 16.291 km，换乘 **1** 次 |
| `beijing` | 草桥 → 金台路 | 21.27 km，换乘 **7** 次 | 22.69 km，换乘 **1** 次 |

北京那组尤其极端：两个站都在 10 号线上，而 10 号线是环线，所以"一次车都不换"绕城半圈就能直达；在直线方向上抄近路的走法反倒要在密集的换乘站之间连着换七次车。

## 数据集

程序启动时自动扫描 `data/` 目录下的 `*/network.json`：

- `guangzhou`（310 站 / 21 线 / 371 段区间）：**真实的广州地铁网络**（含广佛线），由 OpenStreetMap 的线路关系直接还原，站序、换乘关系与官方线网一致，转换脚本见下；
- `beijing`（224 站 / 11 线 / 248 段区间）：**真实的北京地铁主干网络**，由公开站点数据经几何方法还原线路顺序与换乘关系得到，转换脚本见下；
- `metro`（65 站 / 9 线 / 72 段区间）：构造网络，一条环线 + 4 条穿心直径线 + 4 条外围线；
- `demo`（14 站 / 4 线）：故意把 1 号线的"山前"一站抬高绕远，构造出"最短"与"最少换乘"分歧的场景；另含一个不连线的"孤岛站"，用于演示不连通时的异常处理。

广州数据只保留每条线路的**极大交路**（短交路是其它交路的站点子集，直接丢弃）。有分叉或分段运营的线路因此成为多条：3 号线主线 + 天河客运站—海傍贯通交路、14 号线主线 + 知识城支线、12 号线东段 / 西段（当前仍分段运营）。这样天河客运站到海傍是 0 次换乘的直达，符合实际运营。11 号线是环线，站点序列首尾都是赤沙，图里因此存在闭合边。

`data/` 下的任何新目录只要包含 `network.json`，启动时都会出现在数据集下拉框里，不需要改任何代码。字段说明见下。

### JSON 格式

```json
{
  "city": "示例市",
  "stations": [
    { "id": "R01", "name": "中央广场", "x": 0.0, "y": 0.0 }
  ],
  "lines": [
    { "id": "R", "name": "环线", "color": "#B7791F",
      "speed": 44.0, "detour": 1.06,
      "stations": ["R01", "R02", "R03"] }
  ]
}
```

- `x` / `y`：平面坐标，单位 **km**；
- `speed`：该线路的平均旅行速度，单位 km/h，用于估算乘车时间；
- `detour`：**绕行系数**，区间实际里程 = 两站直线距离 × 该系数。必须 **≥ 1** —— 这条约束保证边长不小于直线距离，是 A\* 启发函数可以采纳、从而保证最优性的前提，加载后程序会自动校验；
- `stations`：按行车顺序排列的站点 ID。同一站点出现在多条线路的序列里，就成了换乘站。

### 纯文本格式

`stations.txt` 每行 `id,name,x,y`，`lines.txt` 每行 `线路ID,线路名,颜色,速度,绕行系数,站点1>站点2>站点3`。两种文件均以 `#` 开头的行为注释。

## 接入真实城市数据

`tools/import_real_metro.py` 把一份公开的北京地铁站点数据转换成程序使用的格式：

```bash
py tools/import_real_metro.py
```

数据源在 `tools/source/beijing_subway_station.csv`（取自 Wikipedia 与 OpenStreetMap）。原始数据有两个问题，脚本里都做了处理：**站点没有线路顺序**（用最近邻链 + 2-opt 还原，还原出的 1、2、4、10、13 号线站序与实际完全一致）、**换乘站只记录了一次**（用几何插值补回，共 36 处）。另外还识别并剔除了 10 个坐标明显有误的站点。

处理后的网络只保留最大连通分量——S1 线、西郊线等远郊线与主网之间本来就是弱连接，其换乘关系没能完整还原。详细过程见实验报告 4.4 节。

广州地铁走的是另一条路线——OSM 的线路关系本身就带行车顺序和站名，不需要几何还原：

```bash
py tools/import_guangzhou_metro.py
```

数据源在 `tools/source/guangzhou_osm_stops.json`（Overpass API 于 2026-10-18 抓取的 `route=subway` + `network=广州地铁` 关系，许可 ODbL）。脚本会合并上下行、排除快车、从交路里剥离支线、按站名合并换乘站，并校验同名站点的坐标离散度。重新抓取时把文件开头的 Overpass 查询粘贴到 https://overpass-api.de/api/interpreter 即可。

## 测试

```bash
py tests/test_algorithms.py     # 正确性测试
py tests/test_ui.py             # 界面交互测试
py tests/benchmark.py           # 性能对比实验
```

`test_algorithms.py` 包含 9 组、3060 个断言，覆盖：

- 手工核对过的路径（对应报告第四章的正确性验证）；
- **与朴素枚举法的交叉验证** —— 在小图上枚举所有简单路径求出真正的最短距离，与 Dijkstra 的结果逐个比对；
- **A\* 启发函数的可采纳性** —— 逐点验证 `h(n)` 不超过真实的剩余最短距离；
- 三种算法在可达性上的一致性；
- 边界与异常：起终点相同、两站不连通、站点不存在、删除站点后线路断开、文件格式错误等；
- **数据不变量**：绕行系数 < 1、旅行速度 ≤ 0、坐标含 NaN 或无穷大 —— 这三类数据会让算法**静默**给出错误答案而不是报错，因此必须在加载时就拒绝。

`test_ui.py` 包含 5 组、52 个断言，驱动真实窗口检查交互状态机：搜索动画进行中切换算法／改起终点／点画布选站／开始对比／删除站点之后，按钮不能卡死在"搜索中"；切换算法或改起终点后结果面板与对比表要跟着清空；双击站点只选站、双击空白才回到全览。

`benchmark.py` 做三组对比：三算法在两张网络上的横向对比、启发函数放大系数对搜索规模的影响、以及规则网格上 A\* 失效的特例。

## 想看清算法内部

[docs/算法过程讲解.md](docs/算法过程讲解.md) 逐步推演了三个算法的执行过程：每一轮从堆里弹出了谁、为什么是它、松弛改动了谁的估计值。文中所有数字都来自下面这个脚本的真实输出：

```bash
py tools/trace_algorithms.py                          # 推演 demo 网络的东湖 → 西山
py tools/trace_algorithms.py A1 A5                    # 换一组起终点（站点 ID）
py tools/trace_algorithms.py --dataset beijing 草桥 金台路   # 换数据集，用站名
```

脚本跑完每个算法后，会把推演结果与 `src/solver.py` 的正式实现逐项比对（路径、距离、访问站点数），一致才打印"校验通过"——所以文档里的每一步都可以当作程序的实际行为。

## 重新生成数据

```bash
py tools/gen_network.py
py tools/import_real_metro.py
```

前者用固定随机种子（`20260117`）生成两张构造网络，后者从 `tools/source/` 下的原始 CSV 重新转换出北京地铁网络。两者都是确定性的，任何人重跑都会得到完全相同的数据。

## 文件结构

```
run.py                      程序入口
src/
  models.py                 数据模型：顶点、边、线路、路径、统计量
  graph.py                  图结构：邻接表、动态增删、连通性
  loader.py                 外部数据加载（JSON / TXT）
  solver.py                 算法引擎：Dijkstra / A* / 最少换乘 BFS
  ui/
    app.py                  主窗口与动画调度
    canvas_view.py          网络图画布（缩放、平移、选站、高亮）
    control_panel.py        结果面板（统计、换乘指引、算法对比表）
    theme.py                配色与字体
data/
  guangzhou/network.json    广州地铁（真实数据还原，310 站 / 21 线）
  beijing/network.json      北京地铁主干（真实数据还原，224 站）
  metro/network.json        示例市地铁网（构造，65 站）
  demo/network.json         演示网络（14 站，含孤立站）
tests/
  test_algorithms.py        正确性测试
  benchmark.py              性能对比实验
tools/
  gen_network.py            构造数据的生成脚本
  import_real_metro.py      北京地铁数据的转换脚本
  import_guangzhou_metro.py 广州地铁数据的转换脚本
  trace_algorithms.py       算法推演日志（讲解文档的数据来源）
  source/                   真实数据源（北京 CSV、广州 OSM 原始响应）
docs/
  实验报告.md               五章实践报告
  算法过程讲解.md           三个算法的逐步推演与原理说明
  screenshots/              界面截图
```

三层结构严格分离：`graph.py` 只管图的存储与查询，`solver.py` 只管搜索算法，`ui/` 只管把数据画出来。界面代码中不含任何最短路径计算，算法代码中不含任何绘图逻辑。

## 已知限制

- 权重只计里程，未计入**换乘步行与候车时间**；
- 未考虑线路运营时间和实时拥堵；
- 每次查询独立求解，连续查询之间不复用中间结果。

报告第五章对这几点的改进方向有进一步讨论。
